Make durable state survive a managed control plane

The production deployment failed to boot: `mkdir '/var/task/data'` threw
ENOENT because a Vercel function's filesystem is read-only, and the platform
still wrote durable state to files.

Three real defects, all fixed at the source rather than papered over:

- The identity registry (accounts and sessions) was the one durable store
  still writing raw JSON to a file. It now persists through the storage port,
  so accounts and sessions live in Neon in production, as the architecture
  requires. Every mutation is a serialized read-modify-write, so two concurrent
  serverless instances cannot both accept the same Gmail.
- The data directory is resolved to a writable location and the substitution is
  REPORTED, not hidden. Durable state is unaffected either way, because it is
  in the database; only derived state (local workspace roots, probe records,
  the OpenCode scratch project) uses the filesystem.
- The startup gate's durable-storage probe now exercises the substrate that
  will actually hold the data. Probing a file on a read-only filesystem would
  have reported a healthy foundation while the real database went untested.

`JsonFileStore` moved to `src/storage/snapshot-store.ts`, beside the backends
it talks to; `src/web/durable.ts` re-exports it so every call site is
unchanged.

The supervision trace no longer creates a directory for a file it does not
write: the trace path names a durable slot, and the backend owns the storage.

Backend suite and typecheck are green.
